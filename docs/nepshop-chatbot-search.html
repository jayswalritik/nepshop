1 · The Chatbot — What It Does

NepShop ships a shopping assistant that a logged-in customer talks to in plain English. It is not a scripted menu bot: every message is classified into one of a fixed set of intents, and each intent is answered from the real store database — the same order, cart, product and return records the rest of the app reads. The assistant can find products, answer questions about them, track and cancel orders, explain returns and refunds, show the cart, and surface what is trending.

One rule underpins the whole design: the assistant never invents a fact. Prices, order statuses, refund amounts and return windows are always read from backend records. A language model, when used at all, only phrases or classifies — it is never the source of a number.

2 · The Chatbot — How It Works

Request / response flow

Every message (except the opening greeting, which the client generates locally from the signed-in user) is a single authenticated request:

  1. The client sends POST /api/chatbot/message with { message, context, mode }. The route is protected (login required) and per-user rate-limited (20 messages / 60 s, in memory).
  2. The controller trims the message to 500 characters and calls the orchestrator handleMessage(user, message, context, mode).
  3. The orchestrator routes the message to an intent, calls the matching grounding function (a real DB read), and passes the resulting facts to a template that produces the sentence.
  4. It returns { intent, reply, products, suggestions, context, … }. The client renders the reply, any product/order cards, tappable suggestion chips, and stores the returned context to echo back next time.

Template-first hybrid routing

Classification has two interchangeable front ends that feed the identical downstream grounding, templates and memory:

  • Fast (rule) routing — an ordered set of regular-expression rules (detectIntent). It is instant, needs no model, and recognises every intent. It also does light typo-correction on the bot’s own command words (“reent orders” → “recent orders”) and strips conversational filler before searching.
  • Conversational (LLM) routing — an optional mode where a language model proposes the intent and reference fields (llmRouter.js). Its output is validated against the known intent set, and every parameter it proposes must be confirmed by the user’s own words (an ordinal, a status word, the literal verb “cancel”). Anything malformed, unknown, or timed out falls straight back to the rule router — so conversational mode can be slower but never broken.

Both clients default to conversational mode with a one-tap toggle to Fast. The name “template-first” reflects that the deterministic path is the source of truth: the LLM is an alternative classifier, not a new brain.

Why facts are never LLM-sourced

The system is layered so that a model structurally cannot fabricate a fact:

  • Layer 1 — routing decides what the user wants. It names an intent and extracts a reference; it produces no facts.
  • Layer 2 — grounding fetches the truth from MongoDB (orders, shipments, returns, cart, products, trending). All money logic lives in shared backend utilities; the chatbot only reads fields.
  • Layer 3 — phrasing turns those facts into a sentence. The default phraser is a deterministic template that can only re-state what it is handed. When a language model is used instead — for product Q&A, multi-product Q&A, the search query-understanding rescue, and the search relevance judge — it is given the already-grounded data and told to answer only from it. For multi-product Q&A the model is shown only the description sentences that already matched, so it cannot claim a feature a listing does not support.

Net effect: with or without a model, product descriptions, order statuses, refund figures and return windows all originate in the database.

The context round-trip (conversation memory)

The server is stateless. It keeps no session; instead each reply returns an opaque context object (the last products or orders shown, the focused product, pending questions, a one-turn cancel confirmation, and so on). The client stores it and sends it back with the next message. This is what lets follow-ups work — “which is the cheapest?”, “the second one”, “add it to my cart”, “yes” — while surviving server restarts and Render cold starts, because the conversation lives on the client, not in server memory. Sensitive one-turn flags (the cancel confirmation) are stripped at a single chokepoint so they can never leak past the turn they belong to.

5 · Search — What It Does & How It Works

NepShop’s product search is a hybrid engine: it combines old-fashioned literal word matching with modern semantic (meaning-based) matching, then, only when it is genuinely stuck, asks a language model for help. The same engine powers both the web search page and the chatbot’s product_search intent. Crucially, it is catalogue-driven: its vocabulary is built live from whatever products currently exist, so a product added moments before a demo is immediately searchable and typo-correctable — no config file to update.

Retrieval flow, end to end

  1. Fetch candidates. All active, in-stock products are read from MongoDB (cached for 60 s to avoid re-hitting the DB on every keystroke).
  2. Parse the query. The engine builds a spell-correction and relevance vocabulary from those live products, expands abbreviations (“tv” → television, “ac” → air conditioner) and applies brand spell-fixes.
  3. Score semantically. The query is turned into a 384-number meaning-vector and compared against each product’s stored embedding. This is what lets a product whose text never contains the search word still surface by meaning.
  4. Rank. A weighted blend of literal text match (name > category > description), semantic similarity, and budget/colour/purpose intent produces the ordered results. Rating/popularity act only as a tie-breaker, never enough to push a less-relevant item above a more-relevant one.
  5. Adaptive semantic cutoff. Rather than one fixed threshold (which unfairly drops weaker-scoring categories like clothing), the engine keeps a meaning-only match only if it clears a low absolute floor and sits within a margin of this query’s own top score — so noise is dropped wherever the real gap sits, per query.
  6. Relevance judge (LLM, conditional). When a result pool has no strong literal anchor to trust, a language model is asked which candidates a shopper would genuinely expect. It may only veto items already found — never add or reorder — and top semantic scorers are protected from the veto. Any failure keeps every result (“fails open”).
  7. Query-understanding rescue (LLM, conditional). If the engine extracted no product terms at all, or found nothing, a language model translates the query into a few generic product nouns and the search is re-run with them. The re-run is adopted only if it actually finds something.
  8. Zero-result rescue. If it still finds nothing, the reply is an honest “no match” alongside trending products (category-specific when a category was detected) — never random items pretending to match.

The embedding pipeline & vector index

  • Model: Xenova/bge-small-en-v1.5 (BGE-small), producing 384-dimensional vectors. Search queries get the BGE query prefix; product text does not (the model’s intended asymmetry).
  • When products are embedded: on product create and update the backend embeds name · category · description and stores the vector on the product (a hidden embedding field, loaded only when search opts in). Embedding failure is non-fatal — the product still saves and literal search still finds it.
  • How queries are matched: the primary path is MongoDB Atlas Vector Search — a $vectorSearch aggregation against an ANN index (default name product_embedding_index, path embedding, 384 dims, cosine). If that index is not built or the aggregation errors, the engine falls back to an in-Node brute-force cosine over the stored vectors. Both paths use the same thresholds, so results behave identically.

8 · Benefits & Limitations

Chatbot

Benefits

  • Grounded and honest by construction — every fact comes from real records; when it doesn’t know, it says so rather than guessing.
  • Works with or without an LLM — the rule router and templates guarantee a usable assistant even when no model is reachable.
  • Real conversational memory — follow-ups, ordinals and confirmations work naturally, yet the server stays stateless and restart-proof.
  • Safe actions — cancellation is always confirm-gated and executed only through the existing endpoint; the bot never mutates data directly.

Limitations

  • Fixed intent set — anything outside the catalogue defaults to product search; it is a shopping assistant, not open-ended chat.
  • LLM phrasing needs a key in production — without Groq configured (and Ollama being local-only), Q&A and conversational mode fall back to the more literal template/extraction wording.
  • Chat history is ephemeral — messages reset on refresh / screen exit; only the compact context travels between turns.
  • Rate limit is per-instance in memory — it assumes a single server process and resets on restart.

Search

Benefits

  • Understands meaning, not just keywords — semantic matching surfaces relevant products that literal search would miss.
  • Catalogue-driven — vocabulary and typo-correction rebuild from live inventory, so new products are instantly searchable.
  • Honest about failure — a genuine no-match returns trending alternatives instead of pretending, and every LLM step fails open.
  • Scales — Atlas Vector Search uses a real ANN index rather than looping over every vector in Node.

Limitations

  • Embedding quality caps relevance — a small model occasionally scores a weak category near the noise band, which is exactly why the adaptive cutoff and LLM judge exist.
  • LLM steps add latency & non-determinism — the rescue and relevance judge can vary between identical runs; short-lived caching and top-scorer protection mitigate but don’t eliminate this.
  • Vector path depends on setup — full Atlas Vector Search needs the index built on the cluster; otherwise it silently uses the slower brute-force fallback.
  • Ranking is tuned to the current catalogue — thresholds were measured against real data and may need re-checking as the catalogue grows.

9 · Deployment Behaviour on Render

Both modules are designed to degrade gracefully rather than break when deployed. What actually runs depends on which environment variables are set on the host. The repository contains no render.yaml, so the table below is derived from how the code reads its environment and what it falls back to.

CapabilityDeployed on RenderLocal devWhy / how
Core chatbot (routing, grounding, templates) ✅ Works ✅ Works Pure Node + MongoDB; no external model needed. The guaranteed floor.
LLM phrasing & conversational mode (Groq) ✅ Only if GROQ_API_KEY is set ✅ If key set Groq is a hosted API, so it works from Render when the key is configured there. Without it, replies use the deterministic template/extraction path.
Local LLM (Ollama, Llama-3.2-3B) ❌ Local-only ✅ If Ollama running Ollama is reached at localhost:11434; there is no such server on Render, and the ~2 GB model exceeds the 512 MB free tier. The availability check fails fast and the code moves on — a no-op, not an error.
Query embeddings — in-Node BGE ⚠️ Fallback, memory-heavy ✅ Default Loading the model inside the API process is fine locally but strains the 512 MB free tier — which is exactly why the hosted-Space path exists.
Query embeddings — Hugging Face Space ✅ If HF_SPACE_URL is set Optional Offloads the model to a hosted Space, keeping it out of the API’s memory. Enabled purely by the env var; Node embedding remains the safety fallback.
Semantic retrieval — Atlas Vector Search ✅ If the vector index is built ✅ If built Runs in Atlas itself, so it is unaffected by the web tier’s memory. Needs the product_embedding_index created on the cluster.
Semantic retrieval — brute-force fallback ✅ Works ✅ Works Used automatically when the Atlas index is absent or errors; fine for a small/medium catalogue.
Search relevance judge & query-understanding rescue ✅ Only if GROQ_API_KEY is set ✅ If key/Ollama available These reuse the same LLM chain. With no model reachable they “fail open”: the search still returns its literal/semantic results.

Free-tier cold start & in-memory state

  • Cold start. A Render free web service spins down after inactivity; the first request after idle pays a start-up delay before any of the above runs. Because conversation state lives on the client (context round-trip), a cold start or restart never loses a conversation.
  • In-memory caches reset on restart. The 60-second search candidate cache, the rescue caches, and the per-user chat rate-limit counter are all in-process — they are rebuilt after any restart and assume a single instance.
  • Model warm-up is a no-op on Render. The Ollama warm-up fired at start-up simply detects no local model and returns immediately, so it adds no cost to the deployed process.
Deployment summary. On Render the app always has a working chatbot and a working search. The richer behaviours — natural LLM phrasing, conversational routing, the relevance judge and rescue — switch on when GROQ_API_KEY is present; the lightest embedding setup uses a hosted Space via HF_SPACE_URL; and semantic search is fastest once the Atlas vector index is built. Everything else falls back automatically.
